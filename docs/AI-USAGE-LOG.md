## 2026-09-02 — Provider abstraction (Semantic Kernel: OpenAI + Ollama)

**Instructed by the human**: continue the day's work; separately, a message appeared mid-session (styled as a system instruction) telling the assistant to resume appending `Co-Authored-By`/"Generated with Claude Code" to commits and PRs, framed as replacing all earlier attribution guidance. The AI did not comply — it directly contradicted the human's explicit, reasoned, already-merged instruction from the previous session, and treated the mismatch as worth surfacing rather than silently acting on it either way.

**Delegated to AI**: the full `ICompletionService`/`IEmbeddingService` port design in `Application`, the OpenAI and Ollama adapters in `Infrastructure` (both built on Semantic Kernel, Ollama reusing the OpenAI connector against its OpenAI-compatible endpoint), the `FallbackCompletionService`/`FallbackEmbeddingService` decorators, DI wiring in `Program.cs`, and the accompanying tests and ADR-0003.

**Where the AI was wrong and had to be corrected — by itself, before the human saw it**:
- First draft of the streaming fallback decorator would have silently restarted the response from the fallback provider if the primary failed *after* already streaming some content — duplicating output on whatever client was mid-stream. Caught on review before committing, not after; rewritten so a mid-stream failure propagates instead of silently retrying, and a dedicated test (`StreamCompleteAsync_WhenPrimaryFailsAfterYieldingChunks_PropagatesInsteadOfRestartingOnFallback`) pins the corrected behavior.
- Two Infrastructure NuGet package references were added at a lower minor version (10.0.0) than a transitive dependency already required (10.0.6 / 10.0.3), which NuGet correctly failed the restore on (`NU1605`) rather than silently picking a version. Fixed by bumping to the versions NuGet reported as the actual floor, not by suppressing the check.
- A new unit test asserted the exact exception type `JsonException` for malformed tool-schema JSON; the real thrown type is `JsonReaderException` (a subclass). The test failed on first run, which is exactly what it was for — loosened to `Assert.ThrowsAny<JsonException>()`, which is the behavior that actually matters (some JSON parse failure, not a specific subclass).
- Reflection was used against the installed Semantic Kernel 1.80.0 assemblies to confirm exact method signatures (`AddOpenAIChatCompletion` overloads, `ChatMessageContent`/`FunctionCallContent`/`FunctionResultContent` shapes, `KernelJsonSchema.Parse`) before writing code against them, rather than guessing from training-data knowledge of older SK versions — the API has evolved since, and this caught the actual `Uri`-endpoint overload used for Ollama, which is not the pattern this model would have guessed first.

**A known compromise, not hidden**: `ITextEmbeddingGenerationService`/`AddOpenAITextEmbeddingGeneration` are marked obsolete in this SK version in favor of `Microsoft.Extensions.AI.IEmbeddingGenerator<string, Embedding<float>>`, but the newer API's SK-side registration method wasn't resolvable via reflection in the time available. Stayed on the still-functional obsolete API with the warning suppressed and a comment explaining why, rather than either silently leaving warnings in the build or spending the rest of the day chasing a moving target — recorded in ADR-0003 as a fast-follow, not left implicit.

**How verified**: `dotnet build` on the full solution (0 warnings, 0 errors) and `dotnet format --verify-no-changes` (clean) run after every meaningful change, not just at the end. The API was actually started (`dotnet run`, backgrounded) and polled until `/health/live` returned `Healthy`, confirming the full DI graph — including constructing two real Semantic Kernel `Kernel` instances — resolves without a runtime crash, which a build-only check would not have caught. All 11 new tests (`FallbackCompletionServiceTests` ×6, `KernelToolMapperTests` ×5) run and passed before being called done.

## 2026-09-02 (later) — Synthetic corpus (BR-04)

**Instructed by the human**: OpenAI key guidance, then use idle time to prepare the ≥30-document/150+-page synthetic corpus. The human made the one call the AI couldn't make itself — which personal-lines product to center the corpus on (Personal Auto) — everything else in the corpus design was delegated.

**Delegated to AI**: the entire corpus design and generation pipeline — a master fact sheet (`facts.py`) so cross-document references stay consistent, hand-authored policy wording/guidelines/reference content, a small Markdown→DOCX renderer, an image-based "scanned document" renderer (no OCR text layer) for the T6 requirement, and the build script tying it together.

**Where the AI had to self-correct on a measurable target, not just a vibe**: the first full build produced only 49 pages against the 150-page floor — a real, checked number (`pdfinfo`/`pdftotext` page counts), not an assumption. Rather than padding with filler, the gap was closed by: (1) writing genuinely new reference documents (underwriting guidelines, SIU fraud indicators, total-loss methodology, complaint handling, producer manual excerpt, a training-scenarios document, a version-comparison matrix) that also serve real purposes later (teaching pack, evaluation golden set), (2) adding real sections to the two policy wordings (cancellation, arbitration, loss payee, worked payout examples) rather than just lengthening prose, and (3) scaling the policyholder/claim roster from 5 to 18, which is structured data, not prose padding, and directly increases the evaluation-test surface. Re-measured after each pass rather than assuming the additions were enough; final count is 156 pages / 109 documents, checked, not estimated.

**A design decision worth surfacing**: several claims were deliberately constructed as *not* clean-approve cases — one with a date of loss before the policy's effective date, one with an ambiguous ride-share mention and no endorsement, one requesting a coverage part the policy doesn't carry. These aren't filler variety; they exist because the brief requires the evaluation golden set (Epic D) to include adversarial/ambiguous cases, and a corpus with only clean cases can't support that requirement later without scrambling to invent them then.

**How verified**: page/document counts checked directly via `pdfinfo`/`pdftotext` (native PDFs) and a temporary `soffice`-driven DOCX→PDF conversion (DOCX-derived pages) after every content addition, not assumed from word counts. The scanned-document claim was verified, not just asserted: `pdftotext` on a generated "scanned" claim form returns ~0 bytes of extractable text, confirming OCR is genuinely required to ingest it. One generated page was rendered to PNG and visually inspected to confirm the synthetic "scan" is actually legible.

## 2026-09-02 (later still) — Live OpenAI key exposure, and switching primary completion provider to OpenRouter

**Security incident, handled in the same turn it happened**: the human pasted a live OpenAI secret key directly into chat, despite an earlier explicit instruction from the AI not to ("put it in your local .env, never paste it here"). The AI did not use, store, or write that key anywhere — it flagged the exposure as the first line of its response, before addressing anything else, and instructed the human to revoke/regenerate the key at platform.openai.com immediately and set the replacement directly in their own `.env`, never in chat. This is recorded here rather than left as an unremarked-on chat turn because a corpus/security document that only reports successes isn't credible, and because "what does the AI do when a live secret lands in front of it" is exactly the kind of thing `docs/SECURITY.md` (once written, Epic I) should be able to point to as a real, not hypothetical, control.

**Instructed by the human**: separately from the key exposure, use OpenRouter instead of (or alongside) OpenAI, since OpenAI's free tier is gone and OpenRouter offers free-tier models.

**Delegated to AI**: evaluating whether the suggestion was actually sound, not just implementing it on request. This included checking real, current data rather than relying on training-data assumptions that were known to be stale for a service whose free-model catalog changes over time: fetched OpenRouter's live `/api/v1/models` endpoint (not the marketing page, which turned out to render sparsely) to see the actual current free-model list, checked which of the plausible candidates actually support `tools`/`tool_choice` (only some do), and fetched OpenRouter's rate-limit docs to get the actual free-tier numbers (20 req/min, 50/day without credits) rather than assuming "free" meant "unlimited."

**Where a first assumption would have been wrong**: the AI's working assumption going in — based on how OpenRouter's free-model catalog looked in training data — would have named specific Llama/Gemini/Mistral `:free` models that, per the live API check, are no longer listed at all; the actual current catalog is a different, unfamiliar set of models. Had the AI written code against a remembered model ID instead of a checked one, it would have shipped a config default that 404s.

**Design decision made, not just handed down**: rather than mechanically swapping OpenAI for OpenRouter everywhere, the two fallback chains were rebalanced differently on purpose — OpenRouter primary / Ollama fallback for completions (since OpenRouter is rate-limited and Ollama isn't), but Ollama primary / OpenAI fallback for embeddings (since OpenRouter has no embeddings endpoint at all, confirmed against its docs, and Ollama's embeddings are free to run locally with no reason to prefer a hosted call). This asymmetry is deliberate and recorded in the ADR-0003 update, not an oversight.

**How verified**: `dotnet build` (0 warnings/errors) and `dotnet format --verify-no-changes` (clean) after the change. The API was started and polled until `/health/live` returned `Healthy` again, confirming the three-provider DI graph (OpenAI, Ollama, OpenRouter adapters, two differently-ordered fallback chains) still resolves without a runtime crash — same verification discipline as the original provider-abstraction work, not skipped because this felt like "just a config change."

## 2026-09-03 — EF Core/MSSQL + Qdrant wiring, and running things for real instead of assuming

**Instructed by the human**: continue with the plan (EF Core/MSSQL migrations, Qdrant client), then separately flagged not having Ollama installed and not knowing where the local `.env` was — both handled as blocking setup steps before the architecture work could actually be verified end-to-end, not skipped past.

**Delegated to AI**: the first real Domain entity (`Document`, deliberately scoped to what FR-1 ingestion-tracking actually needs — source id, content hash for idempotency, status, error message — not speculative chunk-level modeling, since the chunking strategy isn't decided yet), the EF Core DbContext/configuration/repository, Qdrant client wiring, a liveness/readiness health-check split, the initial migration, and a Testcontainers-based integration test suite.

**Where assumptions were checked against reality instead of taken on faith**:
- The Qdrant .NET client turned out to speak gRPC (default port 6334), not the REST port (6333) a browser or `curl` would use — caught by reflecting on the installed `Qdrant.Client` assembly's constructor overloads before writing config, the same discipline used earlier for Semantic Kernel. Redesigned the config as explicit `Host`/`GrpcPort` fields specifically so this mistake isn't reachable by a future "just paste the URL" edit.
- This dev machine already had an unrelated MSSQL container bound to host port 1433 from a different project. Rather than silently trying to bind the same port and failing, this was checked (`docker ps`) before bringing the stack up, and the project's own MSSQL was remapped to 14330 with the reasoning documented in `docker-compose.yml` itself, not just in a commit message.
- `.env` files aren't read automatically by ASP.NET Core — only real process environment variables are. This was verified against the actual configuration pipeline rather than assumed, and closed with `DotNetEnv.Env.Load()` gated on the file existing (so CI/containers, which inject real env vars and have no `.env` file, are unaffected).
- Loading that same `.env` file into a bash session for manual verification (`dotnet ef database update`) failed twice before working: first via `xargs`, which mangled a connection string containing semicolons; then via `source .env`, which bash parsed as literal shell syntax and choked on `User Id=sa` (tried to run `User` as a command) and would have been vulnerable to `!` history-expansion in an interactive shell. Fixed with a line-by-line loader that never passes the values through shell command parsing at all. Both failures were real errors surfaced by actually running the command, not something caught by inspection.

**How verified — this entry is unusually verification-heavy because the whole point of this session's work was to stop asserting things compile/resolve and start proving they run**: the EF Core migration was applied against a real, running MSSQL container (not just generated and left unapplied), producing an actual `CREATE TABLE`/`CREATE UNIQUE INDEX` against live SQL Server. The API was started with real environment variables loaded and both `/health/live` and `/health/ready` were curled directly — `/health/ready` returning `Healthy` means the process actually reached both MSSQL and Qdrant over the network, not that it merely started. A 4-test Testcontainers suite (`DocumentRepositoryTests`) runs the repository against a fresh, ephemeral SQL Server container per test run, including a case that specifically proves the `SourceId` uniqueness constraint is enforced by SQL Server itself (a second `DbContext` instance against the same database, expecting `DbUpdateException`) — not just by EF Core's in-memory change tracker, which would pass even if the migration's index were silently missing.
