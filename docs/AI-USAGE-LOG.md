## 2026-09-04 — Chunking/retrieval design (ADR-0004): caught scope-creep through user pushback, not on its own

**Instructed by the human**: before any ingestion code, walk through how extraction, cleaning, chunking, embedding, and vector storage would actually work, including the metadata schema — a deliberate request to design out loud before implementing, matching FR-2's requirement that the chunking strategy be "a deliberate, documented decision."

**What the AI got wrong, and needed two rounds of user pushback to actually fix, not one**:
- First draft proposed one ingestion pipeline for the entire corpus — knowledge documents (policy wordings, guidelines) and case data (declarations, claims) alike — with a single Qdrant metadata schema carrying nullable `policyNumber`/`claimNumber`/OCR-confidence fields to accommodate whichever document type happened to need them.
- The human's first question ("why do we need OCR or ClaimNumber [for company policies]?") was answered correctly in substance — company policy documents themselves don't need those fields — but the AI's fix was incomplete: it kept case data flowing through the *same* vector-search pipeline, just with those fields now clearly attached to "the claims subset," and left open whether claims should be embedded for a hypothetical "ask about a claim" chat feature.
- Only the human's second, more pointed question ("why would we save the claims cases in vector db [at all]") forced the actual reconsideration: case data doesn't belong in a semantically-searched vector store at all, regardless of which fields are nullable, because nothing ever retrieves it by similarity — it's always fetched by a key the caller already has. The AI then had to independently construct the strongest argument *for* embedding it (SIU-style fraud-pattern similarity search) before concluding, on its own reasoning about access control and the project's "no speculative abstractions" rule, that the honest answer was no. That conclusion is recorded in ADR-0004, not just this log — it changes the actual architecture (two ingestion paths instead of one), not merely a docstring.
- This is logged as a two-round failure, not a one-round success, because the first correction addressed the symptom (which fields are populated) without addressing the cause (which documents belong in the pipeline at all) — a reminder that "the human's objection was answered" isn't the same as "the underlying design question was actually resolved."

**Delegated to AI, after the design was settled**: rewriting the `Document` entity and `DocumentCategory` enum to match (dropping `PolicyNumber`/`ClaimNumber`/`RequiresOcr`, dropping the `Declarations`/`Claims` categories and `PdfScanned` format, adding `ChunkCount` for FR-1 status reporting), a new EF Core migration, updating both test suites to the new shape, and writing ADR-0004 to make the reasoning — not just the conclusion — reviewable later.

**How verified**: full solution build (0 warnings), `dotnet format --verify-no-changes` (clean), full test suite (25/25 passing across all 4 projects, including the Testcontainers integration suite), and the schema migration applied against the real running MSSQL container with the generated `DROP COLUMN`/`ADD COLUMN` SQL inspected before running it, not assumed correct from the migration name alone.

## 2026-09-04 (later still) — Retrieval (FR-2): hybrid search, RRF fusion, version-aware filtering

**Instructed by the human**: "continue" — build the next unbuilt epic from the engineering plan. Retrieval (FR-2) was the natural next piece: the corpus was ingested (FR-1) but nothing could query it yet, and the brief calls for a "justified enhancement" beyond plain semantic search plus structured citations and correct refusal on low-evidence queries.

**Delegated to AI, end to end, without a prior design discussion this round** (unlike ADR-0004's chunking design, which the human deliberately walked through step by step before any code): the retrieval strategy choice (hybrid dense+keyword with Reciprocal Rank Fusion), the version-resolution mechanism (a deterministic `PolicyVersionResolver` picking the latest Policy Form edition on or before a given date of loss — directly targeting D2's named wrong-policy-version risk), the BM25 keyword-search implementation and its backing storage, and the API surface, all designed and built in one pass, recorded in ADR-0005 for review rather than walked through interactively first. This is a deliberate difference in process worth naming: for a decision this consequential (D2's own named risk), a fully autonomous design without checkpoint questions carries more risk of the human discovering a disagreement only after the code exists, rather than before — the tradeoff made here was schedule pressure against that risk, not an assessment that no checkpoint was warranted.

**A real architectural fork, decided and documented, not defaulted into**: SQL Server Full-Text Search was the "obvious" choice for MSSQL-backed keyword search, but was checked against reality first — the base `mssql/server` Docker image does not include the Full-Text Search feature component installed by default, and standing it up would have meant either a non-default image variant or a manual component install, real added deployment complexity for a corpus of ~550 chunks. Rather than attempt FTS and discover this mid-implementation, an in-process BM25 scorer (`Bm25Scorer`, pure C#, unit-tested in isolation) computing scores over the MSSQL-filtered candidate set at query time was chosen instead and documented as a deliberate scale-appropriate tradeoff in ADR-0005, not a fallback reached after FTS failed.

**A real schema-migration consequence, worked through rather than glossed over**: adding a `Document.EffectiveDate` column and a new `Chunks` table meant the already-ingested 60-document corpus needed a full re-ingest to backfill both — but re-running ingestion as-is would have been a no-op for every document (the content-hash idempotency check in `KnowledgeIngestionService` short-circuits before reaching either retrieval leg), leaving the new `Chunks` table empty. Recreating `Document` rows fresh would also have generated new internal `Guid` ids, which would have produced *different* deterministic Qdrant point ids than the 552 already stored — leaving old and new points coexisting as duplicates rather than being overwritten. Both `Documents`/`Chunks` (MSSQL) and the Qdrant collection were cleared before re-ingesting, and this was reasoned through and logged here rather than either skipped (leaving `Chunks` empty and retrieval broken) or done silently.

**How verified, against the real running system, not just unit tests**: 18 new unit tests (`Bm25ScorerTests`, `ReciprocalRankFusionTests`, `PolicyVersionResolverTests`) covering the pure algorithmic pieces in isolation — full solution build (0 warnings), `dotnet format --verify-no-changes` (clean), full suite (57/57 passing, up from 33, including the pre-existing Testcontainers integration suite unaffected by this change). The EF Core migration (`AddEffectiveDateAndChunks`) was applied against the real running MSSQL container, and its generated `ALTER TABLE`/`CREATE TABLE` SQL was inspected in the command output before treating it as applied. After the full re-ingestion described above, real HTTP queries were run against the live API: a relevant query ("what is the glass deductible waiver") scored 0.74–0.81 dense cosine similarity on its top three results and was correctly accepted; a deliberately irrelevant query ("what is the capital of France") scored ≤0.39 and was correctly refused, with its top-ranked chunk found by keyword search alone (no dense match at all) — a concrete demonstration that a chunk can surface from one leg without the fused result being treated as confident. ## 2026-09-04 (later still) — Deterministic payout calculation: the arithmetic-hallucination control

**Instructed by the human**: "continue" — the next unbuilt piece. Chose the deterministic payout calculation service specifically (rather than jumping straight to the full multi-agent orchestrator) because `CLAUDE.md` and the brief both flag it as one of two things graders check for in this domain, and building it first gives the orchestrator (still unbuilt) something real to call rather than a stub.

**Delegated to AI**: reading the corpus's own stated formulas (Claims Adjudication Guidelines, Step 4; Total Loss Valuation Methodology, Sections 1/3/5) rather than inventing a generic payout formula independently, implementing each as its own pure Domain-layer calculator, exposing them as agent-callable tools via the existing `ToolDefinition`/`KernelToolMapper` contract from the provider-abstraction work, and writing the full test suite for both layers.

**A real inconsistency this round's own work caught inside the corpus itself, not in the code**: `deductible_selection_reference.md` (written in the earlier corpus-expansion round, for page-count purposes) stated the deductible/limit application order backwards from the corpus's own authoritative formula — it said the deductible is subtracted first and the limit applied as a ceiling afterward, while `adjudication_guidelines.md`'s Step 4 states `payout = min(estimated_damage, applicable_limit) - applicable_deductible`, which caps damage at the limit *first* and subtracts the deductible *after*. These produce different numbers whenever damage exceeds the limit (a $50,000 loss against a $20,000 limit and $500 deductible: $19,500 the correct way, $20,000 the way the reference document described it). This was caught only because implementing the actual calculator required reading the formula precisely enough to code it, not because anyone was proofreading the reference document for internal consistency — a concrete example of why "the corpus and the code should agree by construction" is worth the extra step of citing the exact source formula rather than writing a plausible-sounding one independently. Fixed the reference document's text, rebuilt the corpus, and re-ingested the single changed document (a real exercise of the idempotent-reingestion path from the FR-1 work) to confirm the correction actually reached the live searchable content, not just the source markdown.

**A design choice this round changed its mind about mid-implementation, before merging, not after**: the first draft of the tool executors deserialized a tool call's JSON arguments directly into a C# record with plain `decimal` properties. That's a real, if subtle, defect for this specific codebase: `System.Text.Json` silently defaults a missing property to `0` for a non-nullable value type rather than erroring, which means a tool call missing `estimatedDamage` would have silently computed a confident $0 payout — indistinguishable from a genuinely zero-damage claim, and exactly the "wrong number nobody catches" failure mode this whole piece of work exists to prevent. Caught by asking, while writing the first executor, what actually happens on a missing field, rather than assuming a `[Required]`-style annotation would be needed elsewhere and moving on. Replaced with explicit presence-checking (`ToolArguments.RequireDecimal`) that fails clearly instead of defaulting silently, before any executor was merged.

## 2026-09-05 (later still) — The multi-agent orchestrator itself: prompts, the tool-calling loop, and a genuinely long real-verification story

**Instructed by the human**: "yes proceed and continue" to build the actual orchestrator, with three specific pieces of guidance given up front: write the prompts using XML tags (the human's own prior experience is that this measurably helps instruction-following, and that modern models are trained on enough HTML/XML-structured data for this to transfer), include 2-3 few-shot examples per prompt and never more than 5 (diminishing returns past that point), and verify using the local Ollama model specifically — not OpenRouter — so the hosted free-tier quota stays unspent until the UI is built and ready for a real demo.

**Delegated to AI**: the four prompt files (`prompts/*.md`, each with `<role>`/`<context>`/`<tools_available>`/`<rules or decision_logic>`/`<output_schema>`/`<examples>`/`<final_instruction>` tags and 2-3 worked examples grounded in this corpus's actual synthetic data, per the human's guidance), the shared `AgentRunner` tool-calling loop, the four thin agent wrapper classes, `AdjudicationOrchestrator`, and the approval-gate API endpoints.

**A safety gap the AI found and fixed by actually building the thing, not by re-reading its own prior plan**: ADR-0008 (written in the previous round) had described the write tool as "declared in the Adjudication Drafter's tool set... with execution gated." Writing `AgentRunner`'s actual tool-dispatch loop made clear this framing was wrong: `AgentRunner` executes *any* tool call a model requests, with no approval-gate special case — it was never built to have one, because the write tool wasn't supposed to need it declared at all. Had `finalize_adjudication_decision` actually been included in the Drafter's tool list as planned, the model could have called it mid-draft, before any human review, and the code would have executed it automatically. Caught before any verification run, by asking "what actually happens if the model calls this," not discovered as a live incident. Fixed by never including it in any agent's tool list — it's only ever invoked directly by the API's approval endpoints — and this correction, including that the earlier ADR's own framing was wrong, is recorded in ADR-0009 rather than silently patched.

**How verified — six real end-to-end runs against local Ollama, not stopping at "the code compiles and the fakes pass"**: with `Providers__OpenRouter__ApiKey` deliberately blanked (confirmed in every run's logs: an immediate 401 on the primary leg, then a genuine Ollama call — not assumed from configuration alone), the full pipeline was run repeatedly against the corpus's own CLM-2025-04417 scenario. Four genuine, distinct bugs were found and fixed in sequence, each one only visible by running the real thing:

1. A raw `curl` latency probe against Ollama showed a tool-enabled completion takes ~82 seconds on this hardware versus ~4 seconds with no tools — legitimate model latency, not a hang — but the default 100-second HttpClient timeout was too tight once combined with this project's actual (much longer) agent prompts; the first full run burned ~5 minutes exhausting retries and the degrade-fallback on that same ceiling before failing with nothing computed. Fixed with a longer timeout specific to the Ollama leg.
2. The second run's Coverage Matcher wrote a tool call out as literal JSON text instead of using the model's real function-calling mechanism — a known smaller-model failure mode. `AgentRunner` initially misread this as a non-conforming final answer. Fixed with a structural recovery (scan the content for the tool-call shape and execute it for real) rather than trying to fix it through prompt wording alone, which doesn't reliably fix this for a smaller model.
3. The third run's Coverage Matcher reasoned through every field correctly in plain prose, then wrote the fully correct final JSON as the last thing in its content — direct parsing failed even though the actual answer was right. Fixed by falling back to the last balanced JSON object in the content before giving up.
4. A misleading error message ("failed after 3 attempts") was actually a step-timeout cancellation on attempt 1, not three real failures — fixed to report what actually happened, and per-iteration tool-call logging was added so the next failure wouldn't need another multi-minute run just to see what the model was doing.

After these four fixes, **Coverage Matcher completed correctly, twice in a row** — a real, substantively correct, fully persisted `CoverageMatchResult` (right policy version for the date of loss, right coverage and deductible confirmed against real Declarations data, real citations) — the strongest available evidence that the tool-calling mechanism itself is sound against a real model, not just against hand-written fakes.

**Anomaly Analyst's non-completion was investigated to a real root cause, then reported honestly as a limitation rather than pushed to be "worked around" by another test cycle**: per-iteration logging showed it called `check_damage_value_ratio` in 12 of 12 iterations across two separate runs (once at a 6-iteration budget, once at 12), never progressing to the second tool or a final answer. Before concluding this was a model limitation rather than a code bug, the actual conversation-history representation was checked against the contract tests written earlier this same round (`SemanticKernelCompletionAdapterHistoryTests`), confirming the model's own prior tool call and that tool's result genuinely were represented correctly in what it received — ruling out "the code isn't showing it the answer" as the cause. The conclusion recorded honestly in ADR-0009: this is a real capability limit of this specific local model under a long, detailed prompt, not something more retries or a larger iteration budget would fix (raising 6→12 iterations just reproduced the same non-convergence for longer, which is itself informative). This is exactly the kind of "where the AI/model misled or failed you, and how you verified rather than assumed" disclosure this log exists for — the honest stopping point was reached by diagnosing the real cause, not by giving up after a fixed number of attempts.

**Time and scope judgment made explicitly, not left implicit**: after roughly six real pipeline runs and several hours of wall-clock verification time, continuing to chase full four-agent completion against this specific local model was judged to have sharply diminishing returns against this project's remaining schedule, especially since the user's own stated reason for using Ollama here was temporary (conserving hosted-API quota until the UI is ready) rather than a claim that Ollama must be the verified production path. The call to stop was made after reaching a genuine, diagnosed root cause for the remaining failure — not before.
