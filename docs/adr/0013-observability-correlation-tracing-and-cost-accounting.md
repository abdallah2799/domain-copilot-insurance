# ADR-0013: Correlation IDs, OpenTelemetry tracing, and persisted token/cost accounting

**Status**: Accepted
**Date**: 2026-09-05

## Context

FR-9 requires a correlation ID flowing request → orchestrator → agent → LLM call, traces exported to a self-hosted OpenTelemetry viewer, and per-request token/cost persisted and queryable, plus health/readiness endpoints (already shipped in an earlier round — `/health/live`, `/health/ready`). None of the pieces existed before this change: a real agent run had no way to trace which orchestrator stage or agent call a given log line or slow request belonged to, and the token counts each `ICompletionService` adapter already returns (`CompletionResult.Usage` — this data existed from day one, ADR-0003) were computed and then discarded, never persisted or queryable.

## Decision

**Correlation ID = the request's own W3C trace id**, not an invented identifier. ASP.NET Core starts an `Activity` per incoming request automatically (honoring an incoming `traceparent` header if the caller sent one, since .NET Core 3's built-in W3C trace-context support) — a small `Program.cs` middleware reads `Activity.Current?.TraceId`, sets it as the `X-Correlation-Id` response header, and pushes it into a logger scope so every log line the request produces during its lifetime carries it, without any manual plumbing.

**"Request → orchestrator → agent → LLM call" nesting is ambient, not manually threaded.** `System.Diagnostics.Activity`/`ActivitySource` are BCL types (part of the shared framework since .NET Core 3, no NuGet package needed), so `DomainCopilotActivitySource` (`Application.Observability`) can start child spans directly from `AdjudicationOrchestrator.RunStepAsync` (one span per stage) and `AgentRunner`/`AskService` (one span per completion call) without Application referencing an OpenTelemetry SDK package at all — those spans automatically nest under the same request's Activity via AsyncLocal propagation, which is exactly the FR-9 chain the brief describes, achieved for free rather than built.

**Tracing infrastructure**: `OpenTelemetry.Extensions.Hosting` + `OpenTelemetry.Instrumentation.AspNetCore` + `OpenTelemetry.Instrumentation.Http` + `OpenTelemetry.Exporter.OpenTelemetryProtocol`, wired once in `Program.cs` (the composition root — Application/Domain never reference these packages, only `DomainCopilotActivitySource`'s own `ActivitySource`, per CLAUDE.md's layering rule). `AddOtlpExporter()` is called with no explicit endpoint override — the OTel .NET SDK reads the standard `OTEL_EXPORTER_OTLP_ENDPOINT` env var itself, which `.env`/`.env.example` already had a placeholder for since the initial project scaffold.

**Self-hosted viewer**: a single `mcr.microsoft.com/dotnet/aspire-dashboard` container (docker-compose's `otel-collector` service — named for the role it plays, not literally an OTel Collector binary) accepts OTLP directly with no separate collector process, satisfying "self-hosted tool" without adding a second piece of infrastructure. One real gotcha found by actually starting the container and checking its own logs rather than assuming the well-known port: the image's OTLP/gRPC listener is `18889` internally, not the conventional `4317` — `docker-compose.yml` maps host `4317` to container `18889` so `OTEL_EXPORTER_OTLP_ENDPOINT` can still use the conventional port name on the host side.

**Token/cost accounting**: `ITokenUsageRecorder` (Application port) is called from `AgentRunner` (after every completion call in its tool-calling loop) and `AskService` (both `AskAsync` and `AskStreamAsync`) with a `TokenUsageEntry` carrying the request's own correlation id, agent name, provider/model, and real prompt/completion token counts already present on `CompletionResult`/the final `CompletionChunk`. `EfTokenUsageRecorder` (Infrastructure) persists it via a dedicated `IDbContextFactory<DomainCopilotDbContext>`-created context, not the ambient per-request scoped context every other repository in the same request shares — a cross-cutting write calling `SaveChangesAsync` on that shared context would flush whatever unrelated pending changes happen to be tracked on it at that moment (e.g. a partially-built `AdjudicationCase`), which a genuinely separate context avoids entirely. `ITokenUsageQueryService`/`GetTokenUsage` (`ObservabilityController`) exposes both the recent rows and totals computed over every row, not just the recent page, queryable by any authenticated user and shown on a minimal Angular view.

**Cost is a config-driven estimate, not a live billing API call.** `ModelPricingOptions` maps model name → per-million-token prices; an unlisted model (which includes every model this project's own verification actually used — Ollama's local models and OpenRouter's free-tier model) prices at **$0**, which is the honest number for those, not an unimplemented feature. The two illustrative entries (`gpt-4o-mini`, `text-embedding-3-small`) are published list prices for the one paid provider the fallback chain can reach, not verified against a live pricing API.

**A known gap for `AskStreamAsync`, documented rather than engineered around**: unlike `CompletionResult` (non-streaming), a streamed `CompletionChunk` carries no provider/model name field — only usage, on its final chunk. The streaming path records `completionService.ProviderName` (the fallback chain's own combined name, e.g. `"OpenRouter->Ollama"`) as the closest honest answer for which leg actually served the call, and `ModelName: "unknown (not reported per-chunk)"`, rather than changing the streaming chunk contract project-wide just for this one accounting field.

## Alternatives considered

- **A custom correlation-id header generated per request, ignoring `Activity`** — rejected: it would duplicate what ASP.NET Core's own W3C trace-context support already provides for free, and wouldn't automatically correlate with the OTel traces the dashboard shows.
- **A separate OpenTelemetry Collector container in front of the dashboard** — rejected as unnecessary extra infrastructure; the Aspire Dashboard accepts OTLP directly, so a collector would add a hop with no benefit at this project's scale.
- **Recording token usage from inside each concrete `ICompletionService` adapter (OpenRouter/Ollama/OpenAI)** — rejected: that would need every adapter to independently know the current agent name and correlation id, duplicating context each adapter has no natural reason to hold. Recording once at the `AgentRunner`/`AskService` call site (which already has both) is simpler and can't be missed by a future new provider adapter.
- **Sharing the ambient scoped `DomainCopilotDbContext` for token-usage writes** — rejected once its side effect became clear in review: see the "cross-cutting write" reasoning above. A dedicated `IDbContextFactory`-created context per write is a small amount of extra wiring for a real correctness guarantee.

## Live verification, honestly reported

Verified live against the real running API: the correlation ID middleware (`X-Correlation-Id` response header carries a real W3C trace id on every request), the self-hosted dashboard container actually starting and its OTLP/gRPC port mapping actually working (the `18889`-vs-`4317` finding above was caught this way, not assumed), and `GET /api/observability/token-usage` correctly authenticating and returning a well-formed empty report before any completion call had been recorded.

One live end-to-end attempt (a real `/api/retrieval/ask` call, meant to confirm a recorded row with real token numbers) did not complete: OpenRouter's free-tier key was still 429-rate-limited from this project's own extensive verification activity earlier the same day (the identical constraint FR-3's `docs/EVALUATION.md` already documents), and the Ollama fallback leg exceeded its 600-second `HttpClient.Timeout` before producing a completion — consistent with the 5–25+ minute-per-call Ollama latency already measured and disclosed during FR-3's work, not a new problem this change introduced. Because the completion call itself never returned, `AgentRunner`/`AskService` never reached the `RecordAsync` call, and no row was persisted from that attempt. This is reported here rather than silently retried until it happened to succeed: the two halves of the pipeline this exercises (a completion call handing real usage numbers to `RecordAsync`, and `EfTokenUsageRecorder`/`EfTokenUsageQueryService` round-tripping a row through real SQL Server) are each independently verified — the former by `AgentRunnerTests`/`AskServiceTests` against a fake completion service with real, non-zero token numbers, the latter by `TokenUsageObservabilityTests` against a real Testcontainers MSSQL instance — but chaining them through one specific live external LLM call within this session's time budget did not land.

## Consequences

Every real agent run and ask/ask-stream call now leaves a genuine, queryable trail: a correlation id a caller can grep their own logs against, real per-stage/per-call spans in a running OpenTelemetry viewer, and persisted token counts with an honest (mostly-zero, for this project's actual providers) cost estimate. The gaps that remain are named rather than hidden: `AskStreamAsync`'s recorded model name is a known limitation of the streaming chunk contract, not a bug; the cost table is illustrative for one provider this project doesn't actually spend money through in verification; and the Aspire Dashboard's anonymous-access mode is a local dev/demo convenience, not something a real deployment should carry forward unchanged.
