# ADR-0006: Deterministic payout calculation, never LLM arithmetic

**Status**: Accepted
**Date**: 2026-09-04

## Context

The brief names arithmetic hallucination as one of two specific risks graders check for in this domain: an LLM asked to compute a payout, limit, or deductible figure can produce a plausible-looking but wrong number, with no structural reason a reviewer would catch it beyond re-deriving the math themselves. `CLAUDE.md`'s architecture boundaries already state the non-negotiable rule directly — "Any payout, limit, or deductible calculation is plain C# in `Application`/`Domain`, unit-tested, and never delegated to an LLM. Agents may call it as a tool and must cite its output verbatim" — but a rule stated in a governance document is not itself an enforcement mechanism. This ADR is that mechanism: the concrete design that makes the rule structurally true rather than merely documented, ahead of the multi-agent orchestrator (FR-4/FR-5) that will actually call into it.

The corpus's own Claims Adjudication Guidelines (Step 4) and Total Loss Valuation Methodology (Sections 1, 3, 5) already state the exact formulas a human adjuster follows. The code implements those specific formulas, not a generic "payout calculator" invented independently of the corpus — so an agent's citation of "Claims Adjudication Guidelines, Step 4" and the number it got from calling a tool are describing the same computation, not two things that happen to agree.

## Decision

Four pure, static calculators in `DomainCopilot.Domain.Adjudication` (`StandardPayoutCalculator`, `TotalLossDeterminer`, `TotalLossSettlementCalculator`, `GapCoverageCalculator`), each implementing exactly one cited corpus formula, exhaustively unit-tested including edge cases (capping order, zero-floor, boundary equality). Domain has zero external dependencies (per `CLAUDE.md`), so this arithmetic cannot accidentally acquire an LLM/SDK dependency later without visibly violating the layering rule a reviewer would catch.

These are exposed to agents exclusively through `IPayoutToolExecutor` implementations in `DomainCopilot.Application.Adjudication` — one per calculator, each pairing a `ToolDefinition` (name, description, JSON Schema) with an `Execute(argumentsJson)` method that parses the model's tool-call arguments and calls straight into the matching Domain calculator. There is no other code path by which a payout figure enters this system: the model never computes one itself, and the tool executor never falls back to trusting a model-supplied number instead of running the calculator.

## Alternatives considered

- **Let the model compute the figure and validate it afterward** — rejected outright. Validation-after-the-fact still requires running the same deterministic calculation to check against, at which point the model's own number is redundant at best and a source of confusing disagreement at worst (which figure does a reviewer trust if they differ?). There is no version of "let the LLM do the arithmetic" that doesn't reduce to "compute it deterministically anyway," so the deterministic path is simply the only path.
- **A single generic `CalculatePayout` tool with a mode/type discriminator** — rejected in favor of four distinct tools with distinct schemas. A single overloaded tool would need conditionally-required parameters (e.g., `salvageValueIfRetained` meaningful only in "total loss" mode) that JSON Schema expresses awkwardly, and would blur the corpus citation a result traces back to — "Claims Adjudication Guidelines, Step 4" versus "Total Loss Valuation Methodology, Section 3" are different documents with different applicability conditions (`TotalLossDeterminer` exists specifically to gate which one applies), and keeping them as separate tools keeps that distinction visible in the tool-call trace itself.
- **Silent defaulting of a missing required argument** — the first implementation used `System.Text.Json.Deserialize` into a record with plain `decimal` properties, which silently defaults a missing field to `0` rather than erroring. Caught before merging, not after: a missing `estimatedDamage` would have produced a confident-looking `$0` payout indistinguishable from a genuinely zero-damage claim, which is exactly the failure mode this whole ADR exists to prevent. Replaced with `ToolArguments.RequireDecimal`, which checks the raw JSON for the property's actual presence and fails explicitly (`ToolExecutionResult.Failed`) rather than silently substituting a default.

## Consequences

Easier: a payout figure appearing anywhere in this system (an agent's draft, an approval-gate review, an audit trail) is provably traceable to one of four specific, reviewable, unit-tested functions — "never delegated to an LLM" is checkable by reading `DomainCopilot.Domain.Adjudication`'s dependency list (BCL only) rather than trusting a claim about how the system behaves. Each tool's JSON Schema doubles as the actual input contract enforced by `ToolArguments`, so the schema an agent sees and the validation that runs are the same source of truth, not two things that can drift apart.

Harder: adding a new payout scenario (a coverage part this corpus's formulas don't yet cover) means writing a new Domain calculator, a new executor, and its own tests before an agent can use it — there is no generic escape hatch for "close enough" arithmetic, which is the point, but does mean this boundary has to be deliberately extended rather than casually stretched. The four-tool split also means an agent's prompt/orchestration logic must itself get the *sequencing* right (call `determine_total_loss` before deciding which payout tool to call next) — the tools individually cannot prevent a caller from invoking the wrong one for the situation; that sequencing constraint is stated in each tool's own description text and will need to be verified once the orchestrator that actually calls these exists.

## Verification

37 unit tests across the four Domain calculators (edge cases including the capping-order distinction the corpus's own Deductible Selection Reference initially got backwards — see the AI usage log — the 75%-exceeds boundary being strictly-greater rather than greater-or-equal, and every negative-input validation path) plus 19 tests across the four Application-layer tool executors (valid arguments, a missing required argument failing rather than silently defaulting, malformed JSON, a wrong JSON type, and a Domain-layer validation exception surfacing as `ToolExecutionResult.Failed` rather than an uncaught exception). A contract test (`PayoutToolDefinitionsMapToKernelFunctionsTests`) confirms all four tools' JSON Schemas actually map onto Semantic Kernel function metadata without error, catching a malformed schema now rather than only once an orchestrator tries to register it with a real model. Full solution build: 0 warnings; `dotnet format --verify-no-changes`: clean; full suite: 109/109 passing.
