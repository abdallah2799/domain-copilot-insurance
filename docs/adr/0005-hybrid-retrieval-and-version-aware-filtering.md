# ADR-0005: Hybrid dense+keyword retrieval with Reciprocal Rank Fusion, and version-aware filtering

**Status**: Accepted
**Date**: 2026-09-04

## Context

FR-2 requires retrieval over the knowledge corpus to be more than a single dense-vector nearest-neighbor search: the brief calls for a "justified enhancement" beyond plain semantic search, structured citations traceable to an exact chunk, and correct refusal when the corpus doesn't actually support an answer. D2's own named risk sharpens the requirement further: this corpus has two dated Policy Form editions (PAP-2024-STD, effective 2024-01-01; PAP-2025-STD, effective 2025-06-01) with real, cited differences between them (glass deductible waiver, rental limit, and others — see the Policy Form Version Comparison document), and a retrieval path that can't reliably pick the correct edition for a given date of loss will confidently cite the wrong policy's terms. That failure mode is explicitly called out in the brief as one of two things graders look for in this domain (the other being LLM-computed arithmetic, addressed separately by the deterministic payout service).

Two narrower, separable problems therefore needed a decision: (1) what retrieval strategy to use beyond plain dense search, and (2) how to keep a query pinned to the correct policy version.

## Decision

Hybrid retrieval: run a dense-vector search (Qdrant, cosine similarity) and a keyword/lexical search (BM25) as two independent ranked lists over the same chunk set, and fuse them with Reciprocal Rank Fusion (RRF). Both legs are pre-filtered identically by an optional `RetrievalFilter` (form version, category) before ranking. Version-awareness is handled by a separate, deterministic `PolicyVersionResolver`: given a date of loss, it picks whichever `PolicyForm` document has the latest `EffectiveDate` on or before that date, and that resolved version becomes the retrieval filter — not something either search leg or an LLM infers from the query text. A chunk with no `FormVersion` at all (reference material, most endorsements) always stays visible regardless of which version is resolved, since it isn't tied to a specific edition. Evidence sufficiency (the refusal signal) is a direct threshold check on the top result's dense cosine-similarity score, calibrated empirically against this corpus's real embeddings rather than assumed.

## Alternatives considered

- **Dense-only retrieval** — simplest, and arguably "good enough" for well-phrased natural-language queries, but rejected because it has no defense against a query whose relevant answer uses different vocabulary than embedded (dense recall gap) and provides no independent signal to corroborate a match — every result comes from the same scoring function, so a false-positive dense match has nothing to check it against. Keyword search catches exact-term matches (a specific endorsement code, a defined term from the glossary) that dense search alone sometimes ranks lower than it should.
- **Cross-encoder re-ranking instead of RRF** — a re-ranker (scoring query+chunk pairs directly with a second model) generally outperforms RRF, but requires an additional model call per candidate chunk, on top of an already rate-limited hosted completion provider and a local embedding model; RRF is free, deterministic, and well-understood, at the cost of being a weaker signal than a trained re-ranker. Documented here as a candidate v2 enhancement, not built now, per the brief's guidance to choose one justified enhancement rather than several.
- **SQL Server Full-Text Search for the keyword leg** — the "textbook" choice for MSSQL-backed keyword search, but the base `mssql/server` container image does not include the Full-Text Search feature component installed by default, and standing it up would add real deployment complexity (a non-default image variant or a manual component install) for a corpus of only ~550 chunks. An in-process BM25 implementation (`Bm25Scorer`) computing scores over the filtered candidate set at query time is simpler, fully transparent (unit-testable in isolation, no query-plan black box), and fast enough at this scale — this was a deliberate scale-appropriate choice, not an oversight; it would need revisiting if the corpus grew by orders of magnitude.
- **LLM-based query rewriting to infer the applicable policy version from context** — rejected outright for the same reason the payout calculation is deterministic C# rather than LLM arithmetic: version resolution is exactly the kind of small, high-stakes, mechanically-checkable decision this project's own design principle says must not be delegated to a model that can be wrong with confidence. `PolicyVersionResolver` is a pure, unit-tested lookup instead.
- **Storing chunk text only in Qdrant's payload and running BM25 against that** — would avoid a second storage location entirely, but Qdrant's client doesn't expose a bulk "give me all payloads matching this filter" read cheaply enough to recompute BM25 corpus statistics (document frequency, average document length) on every query without effectively re-implementing a scan against Qdrant instead of MSSQL. Persisting a relational `Chunks` table (populated from the same `VectorRecord` list passed to `IVectorStore.UpsertAsync`, so the two legs can't drift out of sync) keeps the two legs' storage concerns cleanly separated behind their own ports, mirroring how `IVectorStore` already hides Qdrant specifically.

## Consequences

Easier: a query has two independent signals voting on relevance, so a coincidental dense-embedding false positive with no lexical support ranks lower after fusion than a chunk both legs agree on — visible directly in the real end-to-end test below, where an irrelevant query's best result scored barely above the refusal threshold in the *dense* leg alone. Version pinning is a single deterministic function call with its own unit tests, not something buried in a prompt or inferred per-query, so it's directly auditable and can't silently regress when a prompt is tweaked later. Ingestion writes to both legs from the exact same `VectorRecord` list, so there's no separate reindex step to forget.

Harder: two retrieval-side stores to keep synchronized (a shrinking or re-ingested document must be deleted from both `IVectorStore` and `IKeywordSearchIndex` — both calls now happen together in `KnowledgeIngestionService`, but a future write path that touches only one would silently desynchronize them). The BM25 implementation is intentionally simple (no stemming, no stopword list, no synonym expansion) — a real production system at a much larger corpus scale would likely want a dedicated search engine (Elasticsearch/OpenSearch) rather than an in-process scan; documented here as the honest scale boundary of this choice, not hidden. RRF's `k=60` constant is the published default from the original paper, not tuned against this corpus specifically — a genuine limitation, since the two "score" numbers surfaced per chunk (dense cosine similarity, BM25) are more directly interpretable to a human reviewer than the fused RRF score itself, which is why both raw leg scores are still carried through to the citation, not discarded after fusion.

## Verification

Real end-to-end queries were run against the live API (not a unit-test double) after re-ingesting the full 60-document knowledge corpus with the new schema:

- A directly relevant query ("what is the glass deductible waiver") returned its top three chunks with dense cosine scores 0.81 / 0.76 / 0.74 — well above the 0.55 sufficiency threshold — correctly marked `hasSufficientEvidence: true`.
- A completely off-corpus query ("what is the capital of France") returned its best dense match at 0.39 — below threshold — correctly marked `hasSufficientEvidence: false`, with the top chunk found by keyword search alone (`denseScore: null`) demonstrating a chunk can still surface without a strong dense match, while the *overall* result still correctly refuses.
- Version filtering was verified both ways: `dateOfLoss=2024-06-01` resolved to `PAP-2024-STD`; `dateOfLoss=2025-09-01` resolved to `PAP-2025-STD`. An explicit `formVersion=PAP-2024-STD` filter, requeried at `topK=20`, returned zero `policy_wording_v2` chunks and did return `policy_wording_v1` chunks alongside version-agnostic reference material — confirming the filter actually excludes the non-matching edition rather than merely ranking it lower.
- Cross-checked totals after the full re-ingestion: 60/60 documents completed, 552 chunks, agreeing across the ingestion endpoint's response, `GET /api/documents`, Qdrant's `points_count`, and a direct row count of the new `Chunks` table (all four: 552/552/552/552).
- 18 new unit tests (`Bm25ScorerTests`, `ReciprocalRankFusionTests`, `PolicyVersionResolverTests`) cover the pure algorithmic pieces in isolation — term-frequency ranking, rare-vs-common-term IDF weighting, RRF's rank-based (not score-based) fusion behavior, and version resolution's date-boundary edge cases — independent of the real end-to-end run above.
