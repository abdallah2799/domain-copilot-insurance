# ADR-0009: A fixed pipeline orchestrator over four agents, with a shared tool-calling loop

**Status**: Accepted
**Date**: 2026-09-05

## Context

D2's workflow (receive claim → match policy version → evaluate coverage/limits/exclusions → detect anomalies → recommend) and its three named agents (Coverage Matcher, Exclusion Analyst, Adjudication Drafter) were reviewed with the user before any code was written — an explicit design-review pass, the same discipline ADR-0004's chunking design went through. Two corrections came out of that review, one from the user and one from re-reading the assignment brief directly: a dedicated fourth agent, Anomaly Analyst, was added so Exclusion Analyst's job narrows to purely exclusion reasoning over the other agents' typed outputs instead of re-reading the raw claim narrative a second time; and anomaly detection was given its own explicit orchestrator state, matching the brief's own workflow arrow-chain, rather than being silently folded into another agent's step.

FR-5 requires a named, justified orchestration pattern with mandatory controls (max-iteration breaker, per-step timeout, retry-with-backoff, graceful degradation to plain RAG) and requires every run be inspectable step-by-step by run ID. FR-4 requires each agent to have an explicit role, a restricted tool set, typed I/O, and a termination condition, with agents communicating through typed contracts rather than free-form text.

## Decision

A fixed pipeline/state machine (FR-5 explicitly lists this as one of the sanctioned patterns), not an LLM-driven planner or supervisor — the reasoning for that choice was already established in the design review: D2's workflow is a known, fixed sequence, and a fixed pipeline gives OBJ-3 ("no recommendation reaches the adjuster without passing through every prior stage") as a structural guarantee rather than something dependent on correct prompting. `AdjudicationOrchestrator` drives one `AdjudicationCase` (ADR-0008) through `CoverageMatcherAgent` → `AnomalyAnalystAgent` → `ExclusionAnalystAgent` → `AdjudicationDrafterAgent`, in that fixed order, recording each stage's typed JSON output and advancing the aggregate's state machine after each one succeeds.

Every agent shares one `AgentRunner` — the tool-calling loop that is FR-4's "restricted tool set, typed I/O, termination condition" made concrete in one place rather than reimplemented four times: the restricted tool set is whatever list of `IToolExecutor` instances a given agent is constructed with, the typed I/O is the C# generic parameter its final JSON output must deserialize into, and the termination condition is "the model's turn contains no further tool calls." `AgentRunner` also owns two of FR-5's mandatory controls: the max-iteration breaker (a bounded number of tool-call round trips) and retry-with-backoff (each completion call, independent of the provider-level fallback chain already inside `ICompletionService` — this retries the whole primary→fallback chain as a unit, for a genuinely transient failure on either leg). The orchestrator owns the other two: per-step timeout (a linked, canceled-after token wrapped around each agent's entire run) and graceful degradation to plain RAG (below).

Prompts are versioned files under `prompts/*.md` (`CLAUDE.md`: never string literals in C#), each structured with XML tags (`<role>`, `<context>`, `<tools_available>`, `<rules>`/`<decision_logic>`, `<output_schema>`, `<examples>`, `<final_instruction>`) and 2-3 worked few-shot examples grounded in this corpus's actual synthetic data — not a generic prompting template, one written per agent's actual role.

## A safety correction made while building this, not after

The original plan (this session's design-review conversation) described `finalize_adjudication_decision` as "declared in the Adjudication Drafter's tool set... but its execution is gated." Building `AgentRunner` revealed this was unsafe as stated: `AgentRunner` executes *any* tool call the model requests via `IToolExecutor.ExecuteAsync` — it has no approval-gate special case, because it was never meant to need one. If the write tool were included in `AdjudicationDrafterAgent`'s available-tools list, the model could call it mid-draft, before any human has reviewed anything, and `AgentRunner` would execute it automatically. `KernelToolMapper`'s `autoInvoke: false` (referenced in ADR-0008 as the mechanism making this safe) only prevents the *Semantic Kernel SDK* from auto-invoking a tool without this codebase's own code deciding to — it was never a protection against this codebase's own orchestration code choosing to execute a tool it was handed, which is exactly what `AgentRunner` does for every tool in its list.

The fix: `finalize_adjudication_decision` is never included in any agent's `availableTools`. It exists as a complete, tested `IToolExecutor` — satisfying FR-4's "≥1 write/side-effecting tool" as a real, schema-validated artifact — but the only code path that ever calls its `ExecuteAsync` is `AdjudicationController`'s approve/reject/edit-and-approve endpoints, invoked directly by a human's action, never reachable from inside an agent's own tool-calling loop. This is a stronger reading of "never executed without passing the approval gate" than declaring it to the model and hoping the gate holds.

## Alternatives considered

- **A supervisor or planner-executor pattern** — already rejected in the design-review conversation preceding this ADR, for the excessive-agency and OBJ-3 reasons above; not revisited here since building the pipeline didn't surface anything to change that conclusion.
- **A dedicated "submit result" tool per agent, rather than parsing the model's final text as JSON** — considered, since FR-4 asks for typed contracts. Rejected: it would mean every agent needs its own uniquely-named submission tool (four more `IToolExecutor` implementations that do nothing but hand data back), and would reintroduce exactly the kind of tool-declared-but-must-never-really-execute-early problem `finalize_adjudication_decision` just demonstrated is easy to get wrong. Parsing the model's final turn as JSON against a documented schema (enforced by the prompt's `<output_schema>` and validated by `AgentRunner` on parse) achieves the same typed-contract requirement without a tool that has to be simultaneously declared and never truly "executed."
- **A single generic `Agent` class parameterized entirely by configuration (prompt name, tool names, output type) instead of four named classes** — considered for less duplication. Rejected in favor of four thin, explicitly-named classes (`CoverageMatcherAgent`, etc.) because FR-4 and the brief's own review process treat "four distinct, named agents" as a first-class, inspectable part of the system, not an implementation detail to collapse away — a reviewer (or a trainee, per the teaching-pack deliverable) should be able to open one file and see one agent's actual role, not a generic runner plus a configuration table.

## Consequences

Easier: a run's trace is inherently the four JSON blobs plus the status field already built in ADR-0008 — no separate instrumentation needed to answer "what happened in this run." Adding a fifth agent later (if the SIU/fraud-specialist gap noted during the design review were ever closed) means one more thin agent class and one more orchestrator stage, not a redesign.

Harder: `AgentRunner`'s retry-with-backoff cannot fix a call that is *structurally* too slow for the configured timeout, or a model that is simply not going to converge on a final answer — both were found, not hypothesized, during verification (below). A fixed pipeline still can't handle a workflow variant it wasn't built for, the same limitation already named for the pipeline pattern generally in the earlier design review. And a known, honestly-documented one from verification itself: full four-agent completion was demonstrated against a real *hosted-class* model's reliability assumptions, not yet against Ollama specifically — see Verification for exactly where that boundary currently sits and why.

## Verification

Real, not stubbed: every agent tool this system has was already unit-tested with fakes (57+ tests across the prior four PRs). This ADR's job was verifying the *agents and orchestrator* actually work end-to-end against a real model — per the user's explicit direction, against local Ollama specifically, so the hosted OpenRouter leg's limited free-tier quota stays unspent until the UI is ready for a full demo. `Providers__OpenRouter__ApiKey` was deliberately blanked for every run below so the fallback chain could only reach Ollama, never the hosted leg (confirmed in every run's logs: an immediate 401 on the primary leg, then a real Ollama call).

Six full end-to-end runs were executed against `POST /api/adjudication/runs` for claim CLM-2025-04417 (the corpus's own rear-end collision scenario). Four genuine issues were found and fixed along the way, each one only visible by actually running the real pipeline against a real model rather than stopping once the code compiled and the fakes-based unit tests passed:

1. **Timeout too short for real tool-calling latency.** A raw latency check (`curl` directly against Ollama's OpenAI-compatible endpoint) showed a plain completion with no tools returns in ~4 seconds, but a completion with even one tool declared took ~82 seconds on this machine — legitimate model latency for constrained function-calling generation, not a hang. The default HttpClient timeout (100s) was too tight once a real agent's full system prompt and multiple tool round-trips were involved: the first full run exhausted all 3 of `AgentRunner`'s retry attempts and the graceful-degrade fallback itself on the same 100-second ceiling, for ~5 minutes before failing with nothing computed. Fixed with a 10-minute `HttpClient.Timeout` on `OllamaCompletionService` specifically and a correspondingly longer orchestrator `StepTimeout` (later raised to 20 minutes — see point 3).
2. **A tool call emitted as text instead of a structured call.** The second run's Coverage Matcher produced no structured `ToolCalls`, but its content was prose followed by a JSON object shaped like a tool invocation (`{"name": "search_knowledge_base", "parameters": {...}}`) — the model intended to call a tool but expressed it as literal text instead of using the actual function-calling mechanism, a known smaller-model failure mode. `AgentRunner`'s "no tool calls = final answer" logic misread this as a (non-conforming) final answer and failed the step. Fixed with `TryExtractEmbeddedToolCall`: before treating empty `ToolCalls` as final, scan the content for this shape and execute it as a real tool call if found — a structural recovery, not a prompt-wording fix, since prompt wording alone doesn't reliably fix this for a smaller model.
3. **A correct final answer buried in prose.** The third run's Coverage Matcher reasoned through every field in plain prose (no code fence) before writing the fully correct JSON answer as the very last thing in its content. Direct parsing of the whole content failed even though the answer itself was right. Fixed by extending `ParseFinalOutput` to fall back to the *last* balanced JSON object in the content when direct parsing fails, before giving up.
4. **Diagnostics needed to actually see the next failure.** A misleading error message ("completion call failed after 3 attempts") turned out to be a step-timeout cancellation, not a real 3-attempt exhaustion — fixed by letting `OperationCanceledException` propagate distinctly. Per-iteration tool-call logging was added so a subsequent max-iteration failure would be diagnosable without another multi-minute run to reproduce it.

After fixes 1-4, **Coverage Matcher completed correctly end-to-end twice in a row** — a real, well-formed, substantively correct `CoverageMatchResult` (right policy version resolved for the date of loss, right coverage part and deductible confirmed against real Declarations data, right citations), persisted to the real `AdjudicationCases` row in MSSQL and visible via `GET /api/adjudication/runs/{id}`. This is the strongest evidence available that the actual mechanism — tool declaration, execution, JSON-recovery heuristics, state persistence, the full `AgentRunner` loop — works correctly against a real model, not just against fakes.

**Anomaly Analyst did not complete, and this is a documented limitation, not a bug left unfixed.** Per-iteration logging (added per point 4) showed it called `check_damage_value_ratio` in **12 of 12 iterations**, never progressing to `lookup_claim_history` or a final answer, across two separate runs (once at a 6-iteration budget, once after raising it to 12). The full conversation history — including the model's own prior call and that tool's successful result — was confirmed correctly represented at the Semantic Kernel level by the `SemanticKernelCompletionAdapterHistoryTests` contract tests written earlier in this same round; this was checked specifically before concluding the cause, rather than assumed. The honest conclusion: this is a real capability limit of an 8B-class local model under a long, detailed system prompt (full XML structure, three worked examples) — it isn't reliably tracking, within its own context, that a tool question it already asked is already answered, and re-asks it instead of moving on. No amount of retry-with-backoff or iteration-budget raising fixes a model that isn't converging; more iterations just reproduces the same non-convergence for longer, which is exactly what raising 6 → 12 demonstrated.

This is logged here rather than hidden because it's genuinely useful, not because the architecture needed an excuse: the fallback chain (`ICompletionService`) already exists specifically so a hosted model (OpenRouter/OpenAI) — with materially more reliable native function-calling for exactly this kind of multi-step, multi-tool conversation — is the intended path once the UI is ready to demo against it, at the cost of hosted-API quota this verification round was specifically told to conserve. Ollama's real, verified capability after this round is: correct, working tool declaration and execution, and reliable completion for a moderately tool-heavy agent (Coverage Matcher, 3 tools); a documented, not-yet-resolved reliability gap for at least one agent's specific interaction pattern remains, worth a follow-up specifically against a hosted model before claiming full four-agent local-model completion.
