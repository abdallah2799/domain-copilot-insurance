# ADR-0008: Approval-gate state machine as the adjudication run's own aggregate

**Status**: Accepted
**Date**: 2026-09-05

## Context

FR-5 requires the approval gate to support approve/reject/edit-and-approve, all audited, and requires "no recommendation reaches the adjuster without having passed through" the full pipeline (OBJ-3 in `docs/BRD.md`). The Claims Adjudication Guidelines' own Step 5 states this even more strongly: "no recommendation is final, and no payout instruction is executed, without explicit adjuster approval. This is a structural control, not a courtesy step — the system must not be able to bypass it under any configuration." A structural control needs a structural enforcement mechanism, not a hope that the orchestrator (not yet built) always calls things in the right order.

## Decision

`AdjudicationCase` (`DomainCopilot.Domain.Adjudication`) is a stateful aggregate whose own methods are the only way to advance a run: `BeginCoverageMatching` → `RecordCoverageMatch` → `RecordAnomalyFindings` → `RecordExclusionAnalysis` → `RecordRecommendation` → `AwaitingApproval`, then exactly one of `Approve`/`Reject`/`EditAndApprove`. Each `Record*` method both stores that stage's typed output (as a JSON blob — see below) and advances `Status` in the same call, guarded by an explicit check that the case is in the expected preceding status; calling a stage out of order throws `InvalidOperationException` rather than silently skipping ahead. `Status` itself is the run's current stage — `AdjudicationRunStatus` has a distinct value per pipeline state, so "every run inspectable step-by-step by run ID" (FR-5) is answered by one field, not a derived computation.

Each stage's output is stored as a JSON string column (`CoverageMatchResultJson`, `AnomalyFindingsJson`, `ExclusionAnalysisResultJson`, `RecommendationJson`) rather than normalized into per-field columns. The four stages' typed shapes (a coverage match result, anomaly flags, exclusion findings, a payout recommendation) have almost no overlapping fields, so a shared relational schema across them would mean each row carries mostly-null columns — the same reasoning ADR-0004 already applied when it rejected a single knowledge-and-case-data pipeline.

The write/side-effecting tool FR-4 requires (`finalize_adjudication_decision`) wraps exactly the `Approve`/`Reject`/`EditAndApprove` transitions. It is declared in the Adjudication Drafter's tool set like any other tool, but — consistent with `KernelToolMapper`'s existing `autoInvoke: false` discipline, under which no tool is ever auto-invoked by a model — its actual execution is triggered only by the orchestrator, only after a human adjuster has acted through the API. This is the one tool in the system where that gate is load-bearing rather than a formality: it is the only tool that mutates persistent state.

## Alternatives considered

- **A generic workflow/state-machine library** (e.g., a NuGet package providing a fluent state-machine DSL) — rejected as unnecessary weight for a graph this small (5 non-terminal states, 3 terminal outcomes, no branching beyond the single terminal choice). A bespoke enum-driven aggregate, the same pattern already used for `Document`/`IngestionStatus`, is fully sufficient and keeps the mechanism visible in ordinary C# rather than behind a library's own execution semantics — the same reasoning ADR-0005 used to reject Semantic Kernel's own Process Framework for retrieval orchestration.
- **A single mutable "CurrentRecommendation" field updated in place at each stage, with a separate audit log table for history** — rejected in favor of one row per run with per-stage JSON columns. A separate audit log is the right shape when many independent events need querying across many aggregates; here there is exactly one linear history per run, already fully captured by the four JSON columns plus the approval fields, and splitting it into a second table would add a join for no analytical benefit at this project's scale.
- **Making the write tool literally un-callable by the model** (omitted from its tool set entirely, invoked only by the orchestrator's own code with no `ToolDefinition` at all) — considered, but rejected: FR-4 asks for the tool to be part of the agent's declared, restricted tool set specifically so the model can reason about proposing a finalized decision in its natural output, with the *execution* gated rather than the *declaration* hidden. Hiding the tool from the model entirely would satisfy the safety property but not what FR-4 actually asks for.

## Consequences

Easier: "no recommendation reaches the adjuster without passing through every prior stage" is enforced by the aggregate's own guard clauses — a caller (the orchestrator, once built, or a test) that tries to skip a stage gets an exception immediately, not a silently-incomplete run discovered later. A claim can be reopened (Claim Reopening and Internal Appeals Guide) as a genuinely new `AdjudicationCase` row against the same claim number, since `ClaimNumber` is deliberately not unique-constrained — verified directly against real SQL Server, not assumed from the entity definition.

Harder: the JSON-blob columns mean no SQL-level query can filter or aggregate on an individual stage's fields (e.g., "find every run where the payout exceeded $10,000") without deserializing every row's `RecommendationJson` application-side first — an acceptable tradeoff at this project's scale, and one that would need revisiting if reporting across many runs became a real requirement. The write tool's safety depends entirely on the orchestrator (not yet built) actually respecting the "never call this except post-approval" contract stated only in the tool's own description text — nothing in `IToolExecutor` itself prevents a differently-written orchestrator from invoking it early; this is the same structural limit already noted for the payout tools' call-ordering in ADR-0006, now extended to the one tool where getting it wrong would be worse than a wrong number.

## Verification

17 new Domain unit tests for the state machine (the full happy-path pipeline, every out-of-order transition throwing, `Reject` requiring a non-empty reason, `MarkFailed` reachable from any non-terminal status but not from a terminal one), 8 new Application tool-executor tests (`FinalizeAdjudicationDecisionToolExecutor` with a fake repository — approve, reject without required comments failing rather than silently applying an empty reason, edit-and-approve replacing the recommendation, an unknown case id, a case not yet at `AwaitingApproval`, an invalid GUID, an unrecognized decision string), and 4 new Testcontainers integration tests against a real MSSQL instance proving the JSON-blob columns and `DateTimeOffset`/enum-as-string conversions round-trip correctly and that `ClaimNumber` is genuinely not unique-constrained. Full solution build (0 warnings), `dotnet format --verify-no-changes` (clean), full suite: 180/180 passing (up from 150). The EF Core migration (`AddAdjudicationCases`) was applied against the real running MSSQL container, and the full DI composition root was verified to resolve without error by starting the real API process and confirming `/health/ready` returns Healthy — this exercises the actual registration graph, which the Testcontainers tests (constructing `DbContext` directly) do not.
